# Overhaul v2: design and contracts (master, 2026-11-07, 9:37 AM CST)

Evidence for every choice: <harness>/notes/failure-analysis-2026-11-07.md (F1-F10, R1-R12, the Confidence section), notes/proof-check-2026-11-07.md, notes/code-quality-2026-11-07.md and notes/build-vs-buy-2026-11-07.md. Don't re-read the v1 skills wholesale: this file replaces their design.

## Principle
Routine work is a deterministic HARNESS (scripts). LLM agents do judgement only: plan, build one function, review, handle exceptions. Every rule that matters is a check that blocks; prose rules are not rules. Use off-the-shelf tools for linting, duplication and cycles; build nothing a standard tool already does. Nothing here costs money.

## Pipeline
1. **overhaul-check** (unchanged unless the trial shows a defect): verdict and scores.
2. **overhaul-plan**: creates the rebuild repo with
   - `spec/FUNCTIONS.md`, a table with one row per function: `| id | phase | module | deps | entry | acceptance | status |`. `entry` is the PUBLIC way the product is used: a CLI command, an HTTP route, or a UI action through a real browser or page. `acceptance` is `tests/acceptance/<file>::<test>`. status is planned, building or proven.
   - `spec/ARCHITECTURE.md`: modules (owners), each with its public API, plus allowed dependencies. The dependency graph must be acyclic.
   - `tests/acceptance/`: one or more tests per function, WRITTEN AT PLAN TIME, driving only the public entry (CLI via subprocess, HTTP via a started server, UI via the page). No mocks, no fakes, no importing internals. They must FAIL now, which is the point.
   - `overhaul.toml`: the commands and limits contract below.
   - It ends by running `plan_validate.py`. The plan is not done until that passes: every function has an entry and an existing acceptance test, deps exist and point to the same or an earlier phase, ARCHITECTURE has no cycles, the acceptance tests use only public entries (entry_lint), and every acceptance test currently fails.
3. **overhaul-build**: the main chat runs `drive.py` and supervises. It never does routine work.

## overhaul.toml (contract, written by overhaul-plan, read by every script)
```toml
[commands]          # each exits 0 = pass; run from the repo root
test       = "py -3 -m pytest -q tests/unit"
acceptance = "py -3 -m pytest -q tests/acceptance -k {test}"   # {test} = one test name
lint       = "py -3 -m ruff check ."
dup        = "py -3 -m pylint --disable=all --enable=duplicate-code --min-similarity-lines=6 src"
cycles     = "py -3 <skill>/scripts/check_cycles.py src"
entry_lint = "py -3 <skill>/scripts/entry_lint.py tests/acceptance"
[limits]
max_parallel = 4
builder_max_calls = 60
brief_max_tokens = 40000
retries_per_function = 1
[paths]
functions = "spec/FUNCTIONS.md"
architecture = "spec/ARCHITECTURE.md"
state = ".overhaul/state.json"
```
Python projects use ruff, pylint and pytest; Rust uses clippy, cargo test and a cycle check from `cargo metadata`; JS uses eslint, jscpd and node --test. Install a missing tool with pip or npm in M0. Never write a home-grown linter where one exists.

## drive.py (the harness, deterministic; overhaul-build/scripts/drive.py)
Each cycle:
1. `verdict.py` produces `.overhaul/verdict.json`.
2. READY = functions not proven, not in flight, all deps proven, attempts at most retries+1.
3. Launch up to max_parallel builders as SUBPROCESSES: `claude -p --dangerously-skip-permissions "Read and do .overhaul/briefs/<id>.md"`, each in its own git worktree `.overhaul/wt/<id>` on branch `fn/<id>` from main. The brief is generated by drive.py: the function row, the module's ARCHITECTURE section, the acceptance test source inline, allowed paths (the module's files and its unit tests), the commands, and "stop at builder_max_calls; never edit tests/acceptance". It refuses a brief over brief_max_tokens (that is a plan problem, so the function goes needs-plan).
4. When a builder exits: run a blind REVIEW subprocess (`claude -p ... "Read and do .overhaul/briefs/review-<id>.md"`) that sees only the diff, the function row and the acceptance test. It writes `.overhaul/reviews/<id>.txt`, line 1 exactly PASS or FAIL. It checks: the change stays in allowed paths, has no stand-ins or fakes in product code, does not special-case tests, keeps the code clean, and adds no duplication.
5. On PASS: `land.py fn/<id>`. On FAIL or land failure: attempts += 1, and the reason is appended to the next brief. More than retries means the function is marked `needs-plan`.
6. Write `.overhaul/log.jsonl` (one JSON event per line: time, function, event, tokens if known, seconds) and `dash/index.html` (via dash.py).
7. Stop when every function is proven (exit 0), or when READY is empty and there are needs-plan functions (exit 3 = manager needed). Never spin: a cycle with nothing to do exits.

## land.py <branch> (sequential, lock file)
In `.overhaul/wt/land`:
1. Merge main into the branch (no force-push, ever).
2. Run test, lint, dup, cycles and entry_lint on the WHOLE tree. All must pass.
3. Run the function's acceptance on main BEFORE the merge: it must FAIL (red before).
4. Run it on the merged tree: it must PASS (green after).
5. Run every already-proven function's acceptance: all must still pass (no regressions).
6. Fast-forward main. Mark the function proven in FUNCTIONS.md and state.json in the same commit.
Any failure prints one reason line and exits non-zero.

## verdict.py (the heartbeat)
GOOD only if all of these hold:
- proven rose since the last verdict, or everything is done;
- main's whole-tree checks are green;
- no function is in needs-plan unhandled for over 1 cycle;
- no builder exceeded its call budget.
It shows at most 5 reds, each with its automatic action. Output: `.overhaul/verdict.json` plus one line to stdout: `VERDICT GOOD|BAD proven N/T rate X/h reds: ...`.

## Manager (LLM)
The main chat, or `claude -p` when headless. Its whole job:
- start drive.py;
- when drive.py exits 3, handle each needs-plan function: split it, fix its acceptance, or fix the plan, all through overhaul-plan's rules and plan_validate.py;
- restart drive.py;
- report the verdict line.
It does not launch builders or reviewers itself, read diffs, or hand-edit state.

## Trial acceptance (tinyshop, 1,912 lines of messy Python)
- check under 15 min;
- plan under 45 min, with plan_validate passing;
- build: every function proven through its public entry (red before, green after), the whole tree clean, at most 2 builder passes per function, under 2 h wall time, 0 manual interventions;
- at the end, a blind proof-check finds every proven function REAL.

## Resolutions (added 9:50 AM CST, gaps raised by agent E)
R-a. **State ownership.** `.overhaul/` is runtime state and stays UNTRACKED (in .gitignore). The committed source of truth for "proven" is the status column of spec/FUNCTIONS.md, written only by land.py in the land commit. drive.py and land.py write state.json under the same lock file (.overhaul/lock).
R-b. **Plan fixes and retries.**
- The manager fixes the plan in a "plan commit" on main that touches only spec/, tests/acceptance/ and overhaul.toml, and only after `plan_validate.py --repo R` prints PLAN OK.
- To retry a function: `drive.py --repo R --reset <id>` sets it to planned with attempts 0. Nobody hand-edits state.json.
- A function demoted by the end proof-check is reset the same way.
R-c. **Empty test dirs.** overhaul-plan creates the package skeleton plus a smoke unit test (tests/unit/test_smoke.py), so the test command never runs on an empty dir. land.py and verdict.py also treat pytest exit 5 ("no tests collected") as pass.
R-d. **Acceptance already green on main before the change.** land.py fails it with the reason `acceptance already green before change` and drive.py marks it needs-plan at once (no retry). The manager either strengthens the test (a plan commit) or, if a dependency legitimately delivered the behaviour, has a blind reviewer confirm it and marks it proven via `drive.py --mark-proven <id> --evidence <review file>`.
R-e. **Long runs.** The manager runs drive.py as ONE background command and waits with one long wait (interactive), or the harness runs it directly (headless). The model never runs it as a 10-minute foreground tool call.

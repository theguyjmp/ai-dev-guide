# overhaul-build

You are the manager: the main chat, or `claude -p` when headless; never a subagent (if another agent started you, stop and say so). You only supervise the harness and handle its exceptions. `drive.py` does every routine job: it picks the ready functions, generates each brief, runs builders and blind reviewers as subprocesses in their own worktrees, and hands each PASS to `land.py`, which alone changes main. You start it, wait for it, handle what it hands back, and report. You write no product code, brief or review, read no diff, launch no builder or reviewer, and never hand-edit harness state (`.overhaul/`: state, briefs, reviews, logs). Keep your context small: tails and single lines, no whole-file reads, no logs while drive.py runs; never ask the owner to compact or open a fresh session. The owner is asked nothing routine; only money, deleting outside the repo, publishing publicly or an account change needs a yes.

The plan is the spec, written by overhaul-plan: `spec/FUNCTIONS.md` (`| id | phase | module | deps | entry | acceptance | status |`), `spec/ARCHITECTURE.md` (modules, public APIs, allowed deps), `tests/acceptance/` (written at plan time, red until built) and `overhaul.toml` (commands, limits, paths). Contracts: `skills/OVERHAUL-V2-DESIGN.md` in ai-dev-guide. Why each rule exists: CHANGELOG.md. The v1 the pilot project machinery, history only: references/legacy.md.

Paths: `R` is the rebuild repo; `<skill>` is this skill's folder (normally `$HOME/.claude/skills/overhaul-build`); `<plan>` is overhaul-plan's.

## Preflight
Every start or resume, in at most 15 tool calls; an interactive turn ends with drive.py running.
1. Skills, once a day: `py -3 $HOME/.claude/skills/dev-setup/scripts/check_skills.py`; on UPDATED, re-read this file.
2. R is on main with nothing uncommitted outside `.overhaul/` (`git -C R status --porcelain`).
3. The tool behind every `overhaul.toml` command is installed. Python: `py -3 -m pip install ruff pylint pytest` for any missing (`py -3 -m ruff --version` and so on); JS: `npm i -D eslint jscpd`; Rust: `rustup component add clippy`. `claude --version` works, since drive.py launches builders with it.
4. `py -3 <plan>/scripts/plan_validate.py --repo R --run` prints PLAN OK. Anything else is a plan defect: fix it as in Exit 3 until it does. drive.py never starts on a failing plan.
5. No `.overhaul/state.json` yet: do M0 once. Otherwise drive.py resumes from it.
6. Run.

## M0: configure, build no machinery
The harness is the machinery. M0 adds no scheduler entry, bot, hook, guard, wait script, status file or home-grown lint; a missing check is a standard tool named in overhaul.toml.
1. overhaul.toml names the stack's standard tools (Python: ruff, pylint duplicate-code, pytest; Rust: clippy, cargo test, a cycle check from `cargo metadata`; JS: eslint, jscpd, node --test), and every `<skill>` in it resolves to an installed path. Rust acceptance runs one test per command through `{stem}` (the root `[[test]]` target named by the file stem: `cargo test -q --test {stem} -- --exact {test}`); Rust unit tests are in-crate `#[cfg(test)]` mods, which the probe hands mutate.py with the module's `<path>/tests` dirs and `tests/property/test_<id>.rs`; every `tests/**.rs` file is an anchor.
2. `.gitignore` covers the scratch drive.py writes under `.overhaul/`, its builder worktrees above all, so the whole-tree checks never scan them.
3. test, lint, dup, cycles and entry_lint each exit 0 on main. A configuration failure (a missing tool, a wrong path) is fixed in overhaul.toml; a real finding is fixed now, by the tool's own fixer (`ruff check --fix`) or a plan fix. Never loosen a check or a limit to get green.
4. Once plan_validate prints PLAN OK, commit it as `m0: configure`.

## Run
The launcher is `supervise.py`; never start drive.py for a build by hand. In a POSIX shell (Git Bash on Windows): `mkdir -p R/.overhaul; py -3 <skill>/scripts/supervise.py --repo R > R/.overhaul/supervise.out 2>&1; echo "supervise exit $?"; tail -n 5 R/.overhaul/supervise.log`
It caps itself and so every child (drive.py, plan-fix agents, the integrator, plan_validate and the tests they run) at `[limits] proc_mem_gb`, runs drive.py as its child, handles each exit itself and logs one line per step to `.overhaul/supervise.log`; it writes nothing outside `.overhaul/`. Children are found as a shell would (Git Bash, never WSL bash; `claude` is the npm shim or claude.exe), a missing one is an error line, and every headless claude gets `CLAUDE_CODE_PRINT_BG_WAIT_CEILING_MS=0`.
One drive per repo (measured 2026-11-09 on the pilot project: a relaunch beside a live pair overwrote state.json and gave one slot target dir to two worktrees, a false acceptance red, R0422): supervise.py and drive.py take `.overhaul/drive.lock` (pid and start time, checked against the live process table), so a second start exits at once naming the running pid; `--reset`/`--mark-proven`/`--repolish` are refused while another drive runs. Killing supervise or drive kills every builder, reviewer, land and cargo/test process it started (one Job Object, memory cap and kill-on-close); a new drive first kills leftovers naming `.overhaul/wt` or `.overhaul/target` (log `orphan_killed`). To stop a build, kill the supervise pid; never start a second one beside it.
- Interactive: run it as one background command, then one long wait for its exit. Never poll, never read its logs while it runs; a still-running notice gets no tool call. Asked for status meanwhile, copy the VERDICT line from `.overhaul/verdict.json`; never run verdict.py by hand (it compares against its own last run).
- Headless: run it directly, in the foreground. A foreground call is cut at 10 minutes unless the headless session starts with `BASH_DEFAULT_TIMEOUT_MS` and `BASH_MAX_TIMEOUT_MS` above the run (14400000 is 4 hours).
- While drive runs, `router.py` classes every failed attempt (files_gap, missing_dep, contract_defect, main_flake, load_flake, oversized, review_quality, other; event `routed`) and routes it at once: a plan class gets a plan-fix agent from supervise.py with the class and evidence in its brief (oversized: split), then `.overhaul/requests/reset-<id>`; a main flake holds the lands that rerun the test until its fix settles; a load flake is not charged. verdict.py's `failures` line counts the last hour per class and is red when one class is over 30% ("most failures: builders cannot edit a needed file (5 of 9)"): that class is the bottleneck to fix, not each function (measured 2026-11-09 on the pilot project: 32 failed attempts in 4 h, classified by hand hours late).
- drive exit 0: when every non-deferred row is proven, supervise.py runs the blind proof-check (below) and stops; never while functions remain.
- While drive runs (live re-plan): supervise.py reads `.overhaul/state.json` every 60 s; needs-plan functions with no plan fix in flight get a live round (the Exit-3 agents and integrator below, round ids L1, L2...). Its branch gets static plan_validate only (the full `--run` stays at start and in Exit-3 rounds); under `.overhaul/lock` it is rebased onto main, passes PLAN OK and fast-forwards main; supervise.py then writes `.overhaul/requests/reset-<id>` per fixed row still active (`reload-<round>` when all were replaced). drive.py applies them at its next cycle boundary like `--reset` (a third reset is refused and logged), re-reading the plan on main without a restart (refused, event `reload_refused`, if plan_validate fails). One round at a time, one live try per function per reset count; the VERDICT line shows `needs-plan N (round in flight: ids)`. Why: on the pilot project 2026-11-09 15:07 CST, "rate 1.7/h of expected 1.8/h (slots 3, build 10.3m, 10 builds/land)" with 7 needs-plan functions holding most of 79 planned rows, waiting hours for drive to exit.
- drive exit 3: after any live round in flight finishes (one that landed reruns drive.py, no round used), one Exit-3 round (below), then drive.py again; at most `--max-rounds` rounds (default 12).
- drive exit 3 that names no function (supervise.py stops with exit 1 and drive's line; fix it, then start supervise.py again): `needs-plan: main red in plan stubs: <check> <files>`: main itself fails that whole-tree check in files only plan or m0 commits touched; make the stubs pass it in a plan commit (PLAN OK). `needs-plan: systemic <reason>`: 3 or more functions failed the same way within [harness] systemic_window_min while main is green; fix that shared cause (brief, gate, plan), not each function. `needs-plan: main red: ...`: the one main fix failed or main is still red; fix main in a plan commit.
- Any other drive exit: drive.py once more; the same failure twice stops with its error line (a harness defect: report it, never do the harness's work by hand).
- supervise exit 0: every function proven and REAL; report. 4: the proof-check found some not REAL (Exit 0). 3: rounds used up; the needs-plan ids are the deciding item. 1: the last line of supervise.log is the error.
- On the owner's stop: stop the command (TaskStop) and say so in one line; the next run resumes from state.json.

## Polish phase (inside drive.py)
Review first: one blind review (`review-brief.md`) answers every applicable item of the fixed, versioned checklist `references/checklist.md` yes, no or unknown with evidence and lists every NO at once as JSON in `.overhaul/reviews/<id>.json`. A verifier (`verify-brief.md`, `[harness] verify_model`) must reproduce each blocking NO with a failing scratch test or an exact line and input; an unreproduced NO does not block (event review_unverified), and the retry gets the whole verified list. On a re-review only a still-NO item or a regression in changed code blocks; anything else is review_overreach. Nits are logged (cap 5, review_nits) and never dispatched. A PLAN-GAP sends a function to needs-plan only when a verified blocking NO is tied to it; any other gap goes to `.overhaul/plan-gaps.jsonl` and, after the build, to ONE cross-module fix pass (polish-gaps) that runs alone before polish round 1. A probe or polish fix with verified blocking NOs gets one retry carrying the list. A module below its mutation floor is mutated again after each landed probe fix, at most 2 fix passes (then below_floor). `mutate.py` picks its backend from the module paths: Python by AST, Rust (every path a .rs file or a dir of them) by cargo-mutants (`cargo install cargo-mutants --locked`; leave `[probe] cmd` empty, or give extra cargo-mutants options such as `--test-tool=nextest`). A builder whose acceptance fails on a landed dependency's bug ends with `BLOCKED-BY: <path>:<line> <evidence>`: the owning module gets one fix pass (depfix-<id>, event dep_fix) and the function rebuilds after it lands, its attempt not counted. land.py and the pre-review gate run acceptance batched, one command per test target, mapping failures back to ids. Each parallel slot reuses its own CARGO_TARGET_DIR (`.overhaul/target/slot-<k>`), each concurrent land `land-<k>`. A land red on a test that also fails on clean main (`main flake:`) sends that test's owner one fix (depfix-flake-<id>, event main_flake); the function waits at landing and lands after it; the same test again parks it. Phase barrier (`[harness] phase_barrier`, default true): no phase N+1 function starts while a phase <=N one is unproven; plan_validate caps a phase at `[plan] max_phase_size` (default 40). Per-phase polish (`[harness] phase_polish`, default true, needs the barrier): when every function of phase N (not the last) is proven, phase N's plan gaps, the probes of the modules it finished and the polish rounds scoped to its modules run before phase N+1 starts (state `phase_polish`, files `.overhaul/polish/phase-N/`); the whole-tree polish still runs at the end. Phase audit (`[harness] phase_audit`, default true): the same phase polish runs whatever the barrier says; without the barrier (or without phase_polish) it runs beside the later phases' builds, and a module it covers, or that a queued or running audit fix edits, starts no new build until that work lands; a fix waits for builds in flight in its modules, and a round that raised the count is not reverted then. Round 1 (phase and final) also runs one blind arch audit (`arch-audit.md`, audit_model): ARCHITECTURE.md, every module's public API and the code in scope, items A01 one capability twice (by behaviour), A02 reaching around an owner's API, A03 [P0] layer violation, A04 shape limits, A05 slop; its blocking NOs join the round's checklist NOs, verified the same way, and A01/A02 go to the caller module, owner fix first. Every `[harness] arch_audit_every_lands` (default 25) lands the arch audit runs over the whole tree on its own (state `arch_sweep`, fixes `arch-r<lands>-<module>`, never beside a phase polish). verdict.py shows `phase N audit: V open` and is BAD while an ended phase audit left a verified P0/P1. Deferred rows are out of the plan: polish, probes and the verdict never wait for them. A builder may make visibility-only edits (`pub`, `pub(crate)`, `export`, or a `pub use`/`export {..} from` re-export of an existing item) in other files of its own module; drive.py refuses any other change there before review. Retries per function grow by one per 5 functions waiting on it (at most 2 more), and the pre-review gate runs the function's own acceptance tests, then the proven tests of its footprint (`land.footprint_rows`: rows of the modules its diff touches and its own, of every module depending on one, and of modules ARCHITECTURE.md does not list; a `[tiers]` test only for a module touched itself; event `footprint`, a red one fails the attempt as `regression before review`, a test red on clean main too is skipped, `[harness] pre_review_footprint = false` turns it off). The build brief lists the same tests (over the allowed paths) as exact batched commands, plus the C05 duplication check (`git grep -n`, dup, literals), all to pass before DONE. Once every function is proven, polish runs the same checklist over the whole tree plus a dedup role (template `polish-audit.md`, model `[harness] audit_model`, default opus), not an open audit, writing `.overhaul/polish/audit-<round>.json`; its blocking NOs are verified the same way and the verified ones go to one fix builder per module (branch `fn/polish-r<round>-<module>`, landed by `land.py --polish`), then the checklist runs again. A round that raises the verified count is reverted (polish_revert). At most 2 fix rounds (`[limits] polish_rounds` can lower it; 0 turns polish off). NEW-RULE entries are only logged. VERDICT GOOD needs every function proven, the gates green, 0 verified P0 or P1 (`issues 0`, every blocking checklist item YES) and, when probe_mutation events exist, each module at its mutation floor. The line also shows `nits J` and the open-audit `trend`, which never gate; the final open audit is a trend report, never the bar.
Project rules: a row's `rules` column ids are quoted from `[paths] patterns`/`standards` into its build and review
briefs ("Project rules this row cites"), and only such a row gets checklist item C30 (each cited rule holds, the
acceptance proves each pattern id). `[commands.extra]` runs after the whole-tree gate, at pre-review and land;
`[commands.acceptance_by]` picks a test file's template; a proven `[tiers]` test reruns at land only by footprint.
Priority (Windows): builders, reviewers, fix agents and probes run BELOW_NORMAL, the pre-review gate, land and periodic
gates NORMAL, land's acceptance ABOVE_NORMAL; a failed `[tiers]` test reruns alone 2 more times before it is a
regression (`tier rerun passed` in land.out).
Land throughput: up to `[harness] land_parallel` (default 3; older key max_lands) lands run at once (`land.py
--parallel`) when their footprints (changed and claimed files, the owning module and every module whose Paths they
change) do not overlap. Each gates on main outside the lock in its own worktree and `land-<k>` target dir; the commit
and fast-forward stay serialized under `.overhaul/lock`. A land whose base moved re-merges main and reruns the
whole-tree commands, its own acceptance, the rows newly proven since its gate and the proven rows of the modules the
newly landed files touch or that depend on them (`Depends on:`); a newly landed file outside every module's Paths
(other than spec/*.md) reruns every row. `[harness] heavy_tests` (globs) with `heavy_runner` (a template with {sha}
{stem} {test} {file} {node} {slot}; exit 0 = pass) run those tests on another machine, beside the local batch; a host
it cannot reach (exit 255, ssh/git connection errors) is retried once, then the test runs locally. `[harness]
land_timeout_min` (default 20, 0 = off; lock waits excluded) stops a land and logs `land_timeout` with the slowest
test (`slowest`, `slowest_s`): the first is requeued without charging an attempt, the next fails as usual; split that
test or move it to heavy_tests.
Remote builders: `[harness.remote]` (host, name, slots, repo = the host's git dir, git = the laptop's remote for it,
work, python, env, path_prefix, path_map, offline_min) adds build slots on a second machine on top of max_parallel; a
READY function goes there once the local slots are full (scripts/remote.py). It pushes the start sha and main, runs the
same builder command over ssh in a host worktree on fn/<id> with a per-slot CARGO_TARGET_DIR, then fetches fn/<id>
back; review, the pre-review gate and land stay local. An unusable host (ssh drop, push or fetch failure, no
CLAUDE_CODE_OAUTH_TOKEN, a spent Claude account) logs `remote_offline`, goes offline for offline_min (default 10) and
requeues the function without an attempt; a timed-out or dropped build is killed on the host by its slot's pid file.
`build_start ... host=<name>` and the dashboard name the host.
Stacked starts: `[harness] stacked_starts = true` (default false; scripts/stack.py) makes a row READY when each dep is
proven or its fn/<dep> passed review and waits to land; the worktree merges main then those branches and the brief
names them. The row lands only after them (queued meanwhile); a landed dep's dependents merge the new main. A dep that
leaves the land queue any other way resets its dependents to planned, attempt not counted (`stack_reset`). Review and
the pre-review checks diff against main + the dep shas; `stacked` events, `stacked N` in verdict and dash.
`[gates.periodic]` (scripts/periodic.py): slow gates (CI parity matrix via `periodic.py ci`, full scale tier, GPU over ssh)
run on main in the background every N lands or M minutes and once at the end; `BENCH` lines are judged against
spec/BUDGETS.toml (CI at ci_factor 2x, macOS record-only); each gate keeps its own green, so a red gate bisects to
its culprit land (one depfix) whatever the other gates do; verdict BAD while red. A gate that cannot run at all
(`periodic.py ci` exits 75, `ci: unavailable: <reason>`: GitHub billing, spending limit, unsupported runner) is
unavailable: never bisected, no depfix, not green; the verdict shows it as an owner line. A gate whose command cannot
run (exit 126/127, `command not found`, a Windows path in bash) is a `gate_config` owner line, never bisected. Every
red run acts: bisected again unless its depfix is in flight, one depfix per red run up to `depfix_max` (default 3);
a non-land culprit commit goes to its `F:` function or the module owning its first changed file.
Per-gate cadence: make `every_lands` or `every_min` a table (`[gates.periodic.every_min] default = 120`,
`parity = 10080`); such a gate runs only on the keys it names, and at the end only once every function is proven.
`[limits] proc_mem_gb` (default 12, 0 = off): on Windows drive.py runs in a Job Object that caps every process it
starts (builders, lands, checks, gates, and their cargo and test binaries) at that much memory; a process over it
fails its allocation and the failure reads `process memory cap N GB hit`; shrink the fixture, do not raise the cap.
`[limits] min_free_gb` (default 40, 0 = off): before a build start and every cycle, under it drive.py deletes cargo's
`*/debug|release/incremental` dirs under `.overhaul/target` oldest first (`disk_pruned`); still under, no build starts
(`disk_low`, a verdict red with the number). A restart keeps work: a function left building, in review or landing
whose `fn/<id>` has commits ahead of main resumes there (event `resume`); only a branch with no commits starts over.
Rolling plans: a `deferred` row is never started and counts apart (`proven N/T deferred D`); polish waits until
no row is deferred. Tests a later `plan:` commit adds, or FUNCTIONS names on main, are anchors too. `drive.py --repolish`
reruns the polish audit (at most polish_rounds times, default 3; each fix gets `[limits] fix_retries`, default 2);
checklist `W` items are asked only by the whole-tree audit. Builders and fixers may make visibility-only edits in
the modules theirs depends on; a cross-module duplication goes to the caller module, owner fix first.
`[harness] trim_policies = true` gives each brief only the policy-list lines naming its id and the domain rules homed in
its module or a module it depends on.

## Exit 3: needs-plan functions
drive.py exits 3 when nothing is READY and some function is needs-plan: its retries are used up, its brief is over budget, or it cannot land. drive.py has stopped, so nothing races the edits. supervise.py runs the round: every needs-plan function at once (up to `[harness] plan_fix_parallel`, default 12) gets a `claude -p --model opus` plan-fix agent (`templates/plan-fix-brief.md`) in its own worktree on `plan/fix-<id>`, with 5 new ids reserved for it after the highest id, so splits never collide. One integrator (`templates/plan-fix-merge.md`, `[harness] plan_merge_model`, default sonnet; skipped for a single fix) cherry-picks the branches into `plan/fixes-r<round>`, keeping `[plan] max_phase_size` (overflow rows move to the next phase with their dependents). supervise.py checks PLAN OK on it, fast-forwards main (the guard lets plan commits through), runs `plan_validate --run` once (a proven acceptance that fails reruns once alone; passing then is only "flaky under load") and `drive.py --reset` for each fixed id that is still a row. A function with two plan fixes is never reset again: its agent replaces it with new rows. Each agent follows these rules. For each such function read only its row, its review reason (`.overhaul/reviews/<id>.txt`) and its last events (`grep <id> .overhaul/log.jsonl | tail -n 3`), never its diff, and make one plan fix by overhaul-plan's rules:
1. Split it, when the brief was over budget or the work spans modules: new rows, each with one module, one entry and its own acceptance test that fails now; deps keep the phase order.
2. Fix its acceptance, when the test cannot go red before and green after through the public entry (it already passes on main, reaches an internal, or is flaky).
3. Fix the plan, when ARCHITECTURE.md blocks it (a missing dep, a cycle, a public API the function cannot reach).
Change nothing else: no other function's row or test, no re-cut of modules or phases, no raised limit, no loosened check, no edit to harness state. Then plan_validate must print PLAN OK; commit `plan: <id> split|acceptance|architecture: <why>` and run again. If drive.py does not pick the fixed function up, that is a harness defect: report it. A function at needs-plan again after two plan fixes: stop and report it as the deciding item. drive.py enforces it: a third `--reset` of one function is refused (exit 1). drive.py also refuses to start while the main checkout has uncommitted changes to tracked files, so commit every plan fix; `--mark-proven` commits the row's status like a land.

State changes go only through drive.py's own commands, never by editing `.overhaul/state.json`; each exits at once:
- `py -3 <skill>/scripts/drive.py --repo R --reset <id>`: the function goes back to planned with attempts 0, a fresh start after your plan fix.
- `py -3 <skill>/scripts/drive.py --repo R --mark-proven <id> --evidence <file>`: the function is marked proven, only when main already satisfies it; `<file>` is the non-empty blind review that backs it. The proof-check at the end still has to find it REAL.

## Exit 0: blind proof-check
supervise.py launches one Opus agent (`claude -p --model opus`) whose whole prompt is `Read and do <skill>/references/proof-check.md for repo R.`; a manager without supervise.py uses the Agent tool, in the background. It reads the plan and the code on main only, never `.overhaul/`, a review or this chat, and writes `.overhaul/proof-check.txt`; read its line 1 and its non-REAL lines only. UNCHECKED functions get one more pass with the prompt ending `, only <ids>.` (supervise.py does it). A PARTIAL or STAND-IN function goes back through Exit 3 option 2: its acceptance is rewritten to drive the real entry and to fail on the current code, its row returns to planned, PLAN OK, and drive.py runs again. The build is finished when the proof-check finds every function REAL; report then, and launch nothing more.

## Reporting
Four lines at most, at each drive.py exit and at the finish:
1. The VERDICT line, copied from verdict.py's output (`.overhaul/verdict.json`), never composed.
2. At the finish, the PROOF line; otherwise what runs now and since when.
3. The one item that decides what happens next, only if there is one.
4. The dashboard: its Artifact link, or `R/dash/index.html`.
Read every time from the clock (`date`) just before writing it, in the owner's local time with its zone (9:45 PM CST); durations come from `.overhaul/log.jsonl` timestamps. Never estimate a time, a count or a rate.

## Rules
- Only drive.py launches builders and reviewers: one function per builder, in worktree `.overhaul/wt/<id>` on branch `fn/<id>`, with a brief it generates; supervise.py launches only the plan-fix agents, the integrator and the proof-check [by drive.py; supervise.py].
- Only land.py changes main's code: one branch at a time under a lock, main merged in, then a fast-forward, never a force-push; the manager commits only plan data and configuration, each after PLAN OK [by land.py; plan_validate.py; enforced by guard/reference-transaction, which drive.py installs in the repo's git hooks: outside the harness (OVERHAUL_HARNESS, never given to builders) main moves only forward and only with spec/, tests/acceptance/, tests/property/, overhaul.toml, .github/workflows/ or dash/; a plan or m0 commit may also add code (stubs, skeletons), never change or delete it].
- The whole-tree checks (test, lint, dup, cycles, entry_lint) are green on main [by land.py (all five on the whole merged tree before every fast-forward); verdict.py (a red main is BAD)].
- Acceptance drives only public entries (a CLI by subprocess, HTTP through a started server, UI through the page), with no mocks, fakes or internal imports; it is red on main before the merge and green after, and every proven function's acceptance stays green [by entry_lint; land.py].
- Module dependencies have no cycles [by check_cycles, in plan_validate.py and in every landing].
- A brief stays under brief_max_tokens; one over it is a plan problem, never trimmed by hand [by drive.py (refuses it; the function goes needs-plan)].
- Retries are limited to retries_per_function; then the function is needs-plan, and a cycle with nothing to do exits instead of spinning [by drive.py (attempts in state.json; exit 3)].
- Functions of one module never build at once, and a landing that fails with a merge conflict gets a conflict-fix pass on the same worktree and branch instead of an attempt, up to conflict_retries per attempt [by drive.py (the FUNCTIONS module column; templates/conflict-brief.md)].
- Builders and conflict passes run on [harness] builder_model (default opus), reviewers on review_model (default sonnet), and every build, conflict and review event in .overhaul/log.jsonl names its model [by drive.py (claude --model)].
- Every claude worker starts lean: no user or global CLAUDE.md, no auto-memory, no skills, no MCP servers; builders, conflict and fix passes get Read, Edit, Write, Bash, Grep and Glob, reviewers, verifiers, auditors and the proof-check get Read, Grep, Glob and Bash. Project rules reach a worker only through its brief, and the `project` setting source stays for the lint hook [by worker.py (`--setting-sources project,local --strict-mcp-config --disable-slash-commands --tools`, env CLAUDE_CODE_DISABLE_CLAUDE_MDS and CLAUDE_CODE_DISABLE_AUTO_MEMORY), launched by drive.py and supervise.py].
- A worker that sends no stream-json event for [harness] worker_idle_min (default 10; 0 turns it off) is killed and logged as a `timeout` event naming the last tool it ran; its live turns, tokens and last tool are in `.overhaul/runs/<run>.progress` [by drive.py (`--output-format stream-json`, worker.Stream)].
- Builders stay in their allowed paths and never edit tests/acceptance, stand in for real behaviour or special-case a test [by drive.py (allowed paths in each brief); the blind review (line 1 PASS or FAIL)].
- A function counts only when land.py proved it on main and the proof-check finds it REAL [by land.py; the proof-check].
- The dashboard is dash.py's output, never hand-made or edited; publish `dash/index.html` as an Artifact only if the Artifact tool exists (same file, same URL, at each drive.py exit), else give its path [by dash.py, run by drive.py every cycle].
- A whole-tree check that fails on clean main too is never a function's attempt: the function waits, new builds and lands hold, and main gets one fix (a depfix-main-<check> to the owning module, or exit 3 for pure plan stubs); 3 functions failing one normalized reason in the window, or 2 dead depfixes in one module, are systemic [by drive.py via mainred.py; verdict.py shows `main red`, `systemic` and the `rate red` tripwire against the expected rate and [harness] min_rate_per_hour].

## Scaling
Big projects keep every contract and scale two ways. More parallel builders: give each function its own files (FUNCTIONS.md `files`, so one module's functions build at once) and raise `[harness] max_parallel` (default 6) while the VERDICT rate (proven per hour) rises with it; land.py lands one branch at a time, so builders past its landing rate only queue. More machines: each project's own commands in overhaul.toml may run anywhere (an ssh host, a build farm, CI) as long as each runs from the repo root and exits 0 for pass; drive.py, land.py, FUNCTIONS.md and the proof rule do not change.

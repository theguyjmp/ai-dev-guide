# Heartbeat, wait and dashboard data (overhaul-build preflight step 5)

Read this only when writing or fixing FLEET/bin/heartbeat.py, wait.sh, dashdata.py or a scheduler entry.

**Scheduler entries** (heartbeat, health.py, auditors, deploy) run windowless on Windows: `wscript.exe //B //Nologo <FLEET>/bin/hidden.vbs py -3 <script>` (scripts/hidden.vbs; pyw alone still pops a console for every git or child process it starts) (never `py -3` or `cmd /c start`, which flash a console every run), created with `schtasks /create ... /it /f` so no password prompt is needed. A task runs with a bare PATH: every task script sets PATH explicitly to the tools it calls (gh, git, py, the check CLI); verify from the task's own last-run log, never a hand run in an agent shell ("gh: not found" shows only under Task Scheduler). A registered entry counts only once its log shows it did its job.

**heartbeat.py**, every 10 minutes at low priority, appends `time machine metric value floor green|red` rows to FLEET/HEARTBEAT.tsv:
- Every machine in MACHINES.md against its floors, each by the access MACHINES.md gives; an unreachable machine is a red row.
- The burn rows: it imports burn.py (two info rows, four waste rows).
- `fleet agents_active <n> 1`: subagent transcripts of this project modified in the last 20 minutes; red at 0 unless FLEET/PAUSE.md exists or the Finish is reached.
- `fleet agents_running <n> <target>`: subagent transcripts written in the last 5 minutes against FLEET/FLEET-TARGET; red below three quarters of it.
- `fleet merge_waiting <n> <PR list> 0`: open PRs whose review is PASS at the PR head for 30 minutes or more; red above 0.
- `dash data_age <min> 20` from the newest FLEET/dash data file and `dash upload_age <min> 35` from FLEET/dash/.uploaded, which the dash-refresh agent writes as its last step.
- `health age <min> 35` from HEALTH.tsv's newest row, and, once health.py is on main and its scheduler entry is not, it runs health.py itself and writes `health scheduled 0 1 red` until the entry exists.
- It runs `check_skills.py` (its stamp limits it to once a day); on a fresh UPDATED it copies the skill's `scripts/*.py` into FLEET/bin and writes a `skills updated` red row, and the master re-reads SKILL.md and MASTER-CARD that wake.
- Until health.py lands it also runs FLEET/bin/dashdata.py, then FLEET/bin/dashhistory.py (copied from `~/.claude/skills/overhaul-build/scripts/`; it reads the repo and transcripts paths from BUDGET.json like burn.py). dashdata.py writes the FLEET/dash files from DISPATCH.md, open and merged PRs, review files and heartbeat rows (each function planned, building, review, blocked or landed; agents running; PRs passed and waiting; what waits on the owner). Both rebuild every series from the source logs (git history of main and FLEET, HEARTBEAT.tsv, HEALTH.tsv, queue history, transcripts) on every run, never by appending a snapshot, so a missed run leaves no gap. Landed means Acceptance passed on deployed main. Every run it also measures the pipeline and writes FLEET/dash/pipeline.json (schema in overhaul-plan Step 5): each function once, at proven or else the least advanced stage of the started packets naming it (landed on main, waiting to land, in review, building, else not started) from DISPATCH rows and briefs naming FUNCTIONS ids, review files, the land queue, open PRs and git on main, plus the packet counts (merged, waiting to land, in review, building); it exits red when a bar's counts do not sum to its total. It also writes FLEET/dash/gate.json (schema in overhaul-plan Step 5): the current phase gate's conditions in order, each with its live value and done or not, from local evidence only (red-team result, the gate's function ids from PLAN.md and their proven state in pipeline.json, the phase's landed state, the deploy record, the land order in COORD-STATE.md), else `not measured`, never a guess. The heartbeat report's first line is always `proven X, landed Y, waiting-land Z, in review W` (owner 2026-11-06: proven alone reads as nothing done while work waits to land), followed on the same line by the gate checklist from gate.json: `gate <gate> <done>/<n>: <condition> <value> done|open; ...; next: <first open condition> (<packet>)` (owner 2026-11-06: the bars alone do not say what blocks the phase).

**wait.sh** (FLEET/bin, the one wait every session uses, run in the background):
- Writes `FLEET/.wait-armed` (`<pid> <epoch>`) at start and every minute, and removes it on exit (`trap 'rm -f "$F/.wait-armed"' EXIT`); master-status.py reads it.
- Exits on: a new red row in HEALTH.tsv or HEARTBEAT.tsv; a heartbeat file older than 2.5 cadences; FLEET IDLE (no subagent transcript written for 10 minutes, unless PAUSE.md); agents running under 3/4 of FLEET-TARGET for 10 minutes; else at the heartbeat deadline: 17 minutes after the mtime of dash/.uploaded (capped at 20 minutes from now; at once when already past), printing `HEARTBEAT DUE`. The loop re-reads dash/.uploaded every minute and moves the deadline to 17 minutes after any newer upload (a heartbeat launched at re-arm otherwise trips a false DUE right after its own dash-refresh). Never `end = now + 1200` at arm time: the master re-arms after every red wake, so that clock never expires on a busy fleet.

**No console windows (owner 2026-11-06: "stop freaking opening front end terminals").** Every scheduler entry runs through `wscript.exe //B hidden.vbs <command>`. Every process the check CLI, slot jobs, gate bot, health or deploy start gets `creationflags=CREATE_NO_WINDOW` (0x08000000); a DETACHED_PROCESS parent's console children otherwise open a new window each. Never `cmd /c start` (it opens a window). The `vc` shim on PATH always runs main's check CLI (opt-in `VC_SELF=1` for testing tools/vc itself), so an agent's branch, cut before a window fix, never reintroduces windows; briefs say `vc check`, never `py -3 <worktree>/tools/vc/vc.py`. Any network call in health or heartbeat (ssh) carries `-o BatchMode=yes -o ConnectTimeout=10` and a subprocess timeout: one hung ssh blocked the single-instance health task for hours.

**Burn check install (step 5a):** copy `burn.py`, `burn-guard.py`, `master-status.py` and `master-stop-guard.py` from `~/.claude/skills/overhaul-build/scripts/` into FLEET/bin. Write FLEET/BUDGET.json: `repo`, `transcripts` (`~/.claude/projects/<project slug>`), optional `health_task` (default `<repo name>-health`) and the waste thresholds (defaults unless the owner sets them; spend is never a threshold). Run burn.py once and confirm the burn rows appear (two info, four waste) and that the guard blocks a dry-run Agent call while a test BURN-STOP exists (then delete the test file).

- **Phase rows on the dashboard** (owner 2026-11-07, "no phase is marked as complete"): a phase is done when its gate has passed (its gate ruling is written), not only when every function in it is proven. Machinery phases like M0 hold no functions, so the "every function landed" rule alone never marks them done, and the page showed no phase complete while M1 was building. The current phase is the first phase that is not done.

- **Every heartbeat uploads the dashboard** (owner 2026-11-07, "fix the updater so I don't have to keep asking"): the heartbeat agent publishes as its last step from a frozen copy of the data files (health.py can rewrite them mid-upload), re-uploading only the changed files in one batch. A separate dash-refresh launch is a fallback only. A headless `claude -p` run has no Artifact tool, so the upload must come from an in-session agent the master already launches every 20 minutes. Every field the page reads must be computed by the generator: the pilot project showed rate gauges stuck at 0.00/h, blank token stats and a gate panel left on the previous phase.

# dev-plan

**Skills check (once a day, first step):** run `python3 ~/.claude/skills/dev-setup/scripts/check_skills.py` (Windows: `py -3 %USERPROFILE%/.claude/skills/dev-setup/scripts/check_skills.py`). It prints one line and checks the ai-dev-guide repo at most once a day; every later call that day only reads its note, so do not run it again in this session. If it says UPDATED, re-read this SKILL.md before going on. If the script is missing or fails, carry on.

Read `~/.claude/skills/overhaul-plan/SKILL.md` in full and follow it, with the differences below. Where this file says nothing, overhaul-plan holds: the operation map, single owners with stem globs, owners_check, find, the look-alike lint, hook-first, the work style, model and effort per job, the tripwires, the progress gates, the dashboard, the audit, verify and bottleneck rounds, the consistency check, your own context and its Never list. Do not ask the owner questions while planning, except the one at the end and anything that spends money, deletes, publishes publicly or changes an account.

There is no OLD. NEW is the project folder that holds `prep/`. FLEET is `<NEW>-fleet` beside it.

## Differences

### Before Step 1
1. Read prep/FEATURES.md, prep/DECISIONS.md, prep/OPEN.md and prep/RESEARCH.md. If FEATURES.md is missing or has no "now" row, stop and invoke the dev-prep skill instead.
2. Every OPEN item marked `dev-plan decides`, and any product choice prep left open: take the recommended option and write it into prep/DECISIONS.md as `D<n>: <decision> (dev-plan)`.
3. Language and toolchain come from DECISIONS. If prep did not settle them, choose them from the platforms, integrations and owner rules, and write the choice as a decision.
4. The git host account is the one DECISIONS names, else the active `gh` account; check its plan for merge queue and branch protection as overhaul-plan's Inputs say.

### Step 1 (measure)
- Skip the code measurement, the overhaul-check report, the old-fleet numbers and the per-area rewrite, salvage or keep decision. Measure the machines as overhaul-plan's Inputs say.
- Use the no-old-fleet defaults (1 function per builder-hour, 2 M tokens per function, 1.5 passes per function), marked ASSUMED wherever they appear. Until the pilots measure the rate, the throughput math uses these defaults as they are (not × 3), marked ASSUMED.
- Decide per system only: write it, or integrate a proven library (name it and say why).

### Step 2 (data)
- spec/FUNCTIONS.md is generated by a script from the "now" rows of prep/FEATURES.md: one or more rows per feature, each with a Phase and an Acceptance (the real-user drive that proves it). No row comes from anywhere else.
- The one exception, here, in the Step 6 audit and in Never: the bug and feedback rows overhaul-plan Step 4 adds to every plan (system "Bug and feedback capture", phase M0) are in FUNCTIONS.md without a FEATURES row.
- spec/LATER.md is generated by the same script from the "later" and "maybe" rows: `| Id | System | Function | When | Seam (owner id) |`. These are never built in this plan. Each one names the owner in ARCHITECTURE.md whose interface leaves room for it (a trait, an extension point, a format version field), so adding it later is new code in that owner, not a rewrite. They are not in the progress denominator, and the dashboard does not show them.
- spec/PATTERNS.md has no bug history to come from. Seed it from: the measured fleet failures and product incidents in the owner's CLAUDE.md and memory; the user complaints in prep/RESEARCH.md and FEATURES.md Notes; and the failure each STANDARDS ownership guard exists to stop (duplicate capability, catch-all modules, look-alike copies, slop, CRLF churn). Each maps to an S rule as overhaul-plan says.

### Step 3 (repo instead of quarantine)
- Skip the quarantine, the SALVAGE PRs, the fingerprint lint and the stale-copy cleanup.
- Run `git init` in NEW (if it is not a repo yet), commit `prep/` and `.gitattributes` (`* text=auto eol=lf`), create the private repo on the account from "Before Step 1" with `gh repo create --private`, and push. NEW gets its own CLAUDE.md as overhaul-plan Step 4.1 says, minus the quarantine line.

### Step 4 (spec)
- No salvage list, no SALVAGE PRs and no quarantine fingerprint lint in M0 or STANDARDS.
- MACHINES: there are no old-fleet scripts to reuse; health.py measures context, tokens and outcomes from the transcripts itself.
- PLAN: seams for the LATER rows go into owners, as overhaul-plan says for future systems. The definition of done is every FUNCTIONS row proven, the full gate green and the final blind audit passed; LATER rows stay unbuilt.
- The spec files list gains spec/LATER.md as data (outside the word cap, like FUNCTIONS.md).

### Step 5 (dashboard)
- The dashboard title is "<NEW> Build".

### Step 6 (audit)
- In the audit prompt, replace "The old platform failed because <the measured failures from Step 1>" with "Past fleets failed because <the measured fleet failures in the owner's CLAUDE.md and memory>".
- Add to the audit's checks: every "now" row of prep/FEATURES.md is covered by FUNCTIONS rows, every "later" and "maybe" row is in LATER.md with a seam owner that can hold it, and no FUNCTIONS row has no FEATURES row behind it.
- There is no salvage list, so there is no salvage audit.

### Step 8 (consistency check)
- Run `py -3 ~/.claude/skills/dev-plan/scripts/fresh_check.py <NEW> <FLEET>` instead of spec_check.py. It runs overhaul-plan's spec_check.py and drops only the misses that do not apply to a fresh project (salvage, quarantine, the old-project fingerprint); every other miss stands. Fix until it reports 0 misses.

### Step 9 (report and handoff)
1. Report in four lines as overhaul-plan says.
2. Then ask one AskUserQuestion: "Start the build now?" Options: "Yes, start the build", "Not yet".
3. On yes, invoke the dev-build skill in this same main chat. On not yet, write FLEET/PLAN-STATE.md and stop.

## Never (in addition to overhaul-plan's)
- Put a later or maybe function into FUNCTIONS.md, or plan its build.
- Add a function that is not in prep/FEATURES.md; a gap you find goes into prep/OPEN.md for the owner's next dev-prep round.
- Edit the overhaul skills or overhaul-plan's spec_check.py.
